## 記述フォーマット（固定）

ロードマップ項目は以下のテンプレートで記載する。実装手順の詳細はExecPlan（作る場合）か Issue へ集約する。
日付欄は未確定の場合に `未定` / `未完了` を使う。

- `Issue:` には対応する Issue 番号を書く。どの項目にも Issue を作る（まだ無ければ一時的に `未起票` と書き、早めに起票する）。複数書くときは優先順に並べ、着手もこの順にする（番号順ではない）。
- `依存関係:` には未完了の項目名を書く。依存先が完了してアーカイブへ移ったら、`なし（〇〇は完了済み）` と書き換える。
- `ExecPlan:` は着手時に改修規模で作るかどうかを決める。決める前は `着手時に判断`、作らないと決めたら `不要`、作ったらそのパスを書く。
  - 作る目安: 複数の Issue やファイルにまたがって設計判断が要る、DB スキーマ・インストーラ・アップグレード処理を変える、互換性に影響する、数日以上かかる。
  - 作らない目安: 1 つの Issue で原因と直し方がはっきりしている小さな修正。記録は Issue と PR で足りる。

標準の形:

```md
### <タスク名>
- Status: `NEXT | WIP | DONE | BLOCKED`
- Issue: #123, #456 または `未起票`
- 着手予定日: `YYYY-MM-DD` または `未定`
- 完了日: `YYYY-MM-DD` または `未完了`
- 目的:
- 背景/課題:
- 到達条件（Definition of Done）:
- 非対象（やらないこと）:
- 依存関係:
- ExecPlan: `.agent/plans/YYYY-MM-DD-task-name.md` / `着手時に判断` / `不要`
- メモ/判断ログ:
```

不具合修正をまとめた項目は、短い形でよい。目的・背景・到達条件は Issue を正とし、到達条件は「`Issue:` の Issue がすべて閉じている」とみなす。日付欄（`着手予定日` / `完了日`）は短い形でも省かない（完了処理と `/doc-audit` が使うため）。

```md
### <タスク名>
- Status: `NEXT | WIP | DONE | BLOCKED`
- Issue: #123, #456
- 着手予定日: `YYYY-MM-DD` または `未定`
- 完了日: `YYYY-MM-DD` または `未完了`
- 内容: Issue ごとの一言（例: #123 〇〇で××になる）
- ExecPlan: `着手時に判断` / `不要` / パス
- メモ/判断ログ:
```
