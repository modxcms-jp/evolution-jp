# ExecPlan: 管理画面の入力の扱いと、状態を変える操作の CSRF 対策を土台から揃える

## Purpose / Big Picture

管理画面の処理（processor）がリクエストの値を受け取る書き方と、状態を変える操作を受け付ける条件を、決まった一つの方式に揃える。個々の箇所を見つけ次第直すのではなく、入口のヘルパーと判定を一か所にまとめ、新しく書くコードも自然に安全になり、CI で逸脱を検出できる状態にする。Issue #493 の対応。

## Surprises & Discoveries

- 2026-10-12（M1）: `(int)` で id を読んでいた処理は、`12abc` のような値を 12 として扱い、別のリソースを操作していた。M1 で、id が整数として読めないときはエラーで止めるようにした。
- 2026-10-12（M1）: ゴミ箱を完全に削除する処理は、id が正しい形でないと「id なし」と同じ扱いになり、ゴミ箱の全件を削除する分岐に入っていた。M1 で、id が指定されていて整数として読めないときは止めるようにした。
- 2026-10-12（M1）: 要素の編集画面を開いて変更せずに保存すると、本文の改行が `\r\n` に、`NULL` の項目が空文字に、スニペットとプラグインのプロパティが `&NULL=undefined;;` に、テンプレート変数の `elements` が文字列の `(null)` に変わる。main でも同じで、M1 の変更とは関係ない。プロパティと `(null)` は不具合なので、別の Issue で扱う。

- 2026-10-13（M2）: シェル（`shell.js`）は、断片でない応答や通信の失敗のあと、同じ URL をヘッダーなしで開き直すことがある。ヘッダーだけでトークンを渡すと、開き直しで 403 になるか、操作が 2 回走る。このため、GET で状態を変える呼び出しは、シェル経由でも URL にトークンを付ける。
- 2026-10-13（M2）: リソースの保存（`a=5`）は、GET で呼ぶと POST の値が空のまま新規作成の扱いになり、空のリソースを作っていた（main で確認）。保存系の processor も一覧に入れ、GET では実行されないようにした。
- 2026-10-13（M2）: 既存の POST 検証の除外（`a=8`）は、アクション番号が文字列のまま厳密比較していたため、実際には除外されていなかった。ログインの POST はログイン済みの判定より前に終わるので、除外そのものを削除した。
- 2026-10-13（M3）: lint を入れると、M1・M2 のあとも、processor でリクエスト値をエスケープ・整数化せずに SQL へ渡す箇所が残っていた（ユーザー・Web ユーザー・モジュール・テンプレート変数の保存）。どれも保存の権限があるログイン済みの管理者だけが通る経路で、CSRF は M2 で塞がっている。行ごとの検索では、値を変数や配列に入れてから渡す書き方を拾えず、M1 の棚卸しから漏れていた。
- 2026-10-13（M3）: バックアップからの復元（`a=305`）は processor を読み込むが、M2 の一覧に入っていなかった。POST の値だけで動くので GET では何も起きないが、保存系と同じく一覧に加えた。
- 2026-10-13（M3）: 旧 API の `webAlert()`（`ex_deprecated.php`）は、メッセージを `db()->escape()` と `addslashes()` で二重に処理し、`setTimeout` の文字列の中の文字列として `<script>` に埋め込んでいた。`js_literal()` と関数式に置き換えた。
- 2026-10-14（M4）: 修正前の保存処理では、不正な値が混ざると、先に既存の行を消してから INSERT が失敗し、データが消えていた。テンプレート変数のテンプレートの割り当ては 0 件になって 500 に、ユーザー設定は全件消えたうえで画面は成功時と同じ遷移になり、ログにも残らなかった。M3 の修正のあとは、どちらも正しく保存される。
- 2026-10-14（M4）: リソースの編集画面（`a=27`）は、M1 より前から `request_intvar()` で id を読んでおり、`5abc` は id=0 になり、新規作成と同じ形の空のフォームを出す（前後で差なし）。要素の編集画面は `abort_if_invalid_id()` でエラーにしているので、そろえるかどうかは別に判断する。
- 2026-10-13（M2）: 検証環境（サンプルサイト）の管理者では、メッセージ画面（`a=10`）が権限なしで表示できない（main でも同じ）。メッセージの削除は、直叩きでの拒否だけを確認した。

- 2026-10-11（レビュー #506 で判明）: `manager/includes/accesscontrol.inc.php` の POST 向け CSRF 検証が、ログアウト（`a=8`）を「ログイン処理」として検証から除外している。ログアウトはセッションを破棄する更新操作であり、本来は保護対象。M2 で是正する。
- 2026-10-12（着手前の再調査）: Issue #493 に例として挙げた公開・非公開の processor は、id の整数化がすでに済んでいる（`intval()` と、#490 で入れた `(int)`）。整数化されずに SQL に入る受け取り方は、document 系では下書き（リビジョン）関係と移動の処理に残っており、下書きの処理では、値が `manager/includes/extenders/ex_revision.php` の SQL へエスケープされずに渡る。ほかのディレクトリにも数件ある。具体的な箇所は M1 の棚卸しで確かめる。
- 2026-10-12（同）: processor によって、権限の確認のしかたがばらついている（`checkPermissions()` でリソースごとに確かめるもの、`hasPermission()` だけのもの、ログインの確認だけのものがある）。移動の処理では、権限を確かめているのが移動先だけのものがある。M1 で id を揃えるときに、あわせて権限の確認の有無も一覧にし、足りないものは同じ PR で直す。
- 2026-10-12（同）: GET で状態を変えるアクションは document 系に限らず、要素の削除・複製、ユーザー・ロールの削除、アクセス権の操作、ログを空にする操作、バックアップ、ファイルの操作（`a=31` のサブ操作）、ロックの解除、ログアウトなど、およそ 20 系統ある。M2 の一覧は、これらを含めて作る。
- 2026-10-12（同）: GET の URL にトークンを付ける共通の関数は、PHP にも JS にもまだ無い（`csrf_token=` を含む URL は見つからない）。また `.agent/roadmap.md` には、この計画に対応するタスクが無い。
- 2026-10-11（1.2.2J の作業で確認）: DBAPI は全体が「値は呼び出し側で安全化してから渡す」取り決めで動いている。`where()` に加えて、`db()->update()` / `insert()` に配列で渡した値も、`'%s'` で囲むだけでエスケープされない（`manager/includes/extenders/dbapi/mysqli.inc.php` の `update()`）。`select()` などの条件文字列も同じ。安全化の付け忘れは `where()` の呼び出しに限らず、配列の値・文字列の連結にもある。

## Decision Log

- 2026-10-10 / yamamoto・Claude: SQL の条件を組み立てる `where()` が値をエスケープしていなかった件は、先行して #505 で直した（`where()` の中でエスケープする）。この ExecPlan は、その土台の上で、入力の受け取り方と CSRF を揃える。
- 2026-10-10 / yamamoto・Claude: id の受け取りには新しいヘルパーを作らず、既存の `request_intvar()` を「整数を返す」ように改めて統一する。AGENTS.md の「局所的な新方式の導入は禁止。改善は横断的に適用する」に従う。代替案（`request_id()` の新設）は、既存の 47 か所の呼び出しと二系統になるため採らない。
- 2026-10-10 / yamamoto・Claude: CSRF は、状態を変えるアクションの一覧を一か所で定義し、メソッド（GET / POST）によらずトークンを必須にする。すべてを POST に変える案は、呼び出し元（リンク・ツリーのメニュー・ボタン）の作り替えが大きく、段階的に移行できないため、この ExecPlan では採らない。将来 POST に寄せる場合も、一覧はそのまま使える。
- 2026-10-10 / yamamoto・Claude: トークンは、シェル（`EvoShell`）の fetch では既存どおり `X-CSRF-Token` ヘッダーで、フルページの遷移（`location.href` への代入やリンク）では URL の `csrf_token` パラメータで受け取る。URL に載ったトークンはアクセスログや Referer に残り得るが、トークンはログアウトで破棄されるセッション単位の値であり、GET で状態が変わる今の状態よりは大きく改善するため許容する。
- 2026-10-10 / yamamoto・Claude: CI での検出は、DB に接続しない単独の PHP スクリプトにする。`php evo` の CLI は DB 接続を前提にしているため、DB のない CI では使えない。
- 2026-10-10 / yamamoto・Claude: このリポジトリは公開されているため、まだ直していない具体的な箇所の一覧はこの ExecPlan に書かない。M1・M2 の最初に、棚卸しのコマンドで手元に一覧を作って作業する。
- 2026-10-11 / Claude（レビュー反映 #506）: id の検証は受け取り元によらず同じにする。PHP の `(int)` は `"5abc"` を `5` にしてしまい「数字以外は 0」を満たせないため、`(int) postv()` は使わず、POST 限定でも厳密に検証する `post_intvar()` を用意する。
- 2026-10-11 / Claude（レビュー反映 #506）: 同じアクション番号で表示と更新を兼ねる処理（`a=31` の `mode=delete` など）があるため、CSRF の一覧はアクション番号だけでなくサブ操作も見る組で定義する。将来は更新を別アクションへ分けるのが望ましいが、この計画の範囲では番号＋サブ操作とする。
- 2026-10-11 / Claude（レビュー反映 #506）: CSRF 検証はメソッド（GET/POST/HEAD）によらず、一覧に該当する操作で行う。現状の `is_post()` 限定は GET・HEAD で迂回できる。あわせて、既存の POST 検証が `a=8`（ログアウト）を「ログイン処理」として除外しているのは誤り。除外するのは認証前でトークンを持てないログインだけとし、ログアウトは一覧に含める。
- 2026-10-11 / Claude（レビュー反映 #506 CodeRabbit）: 既存の「ログイン以外の POST は検証」は置き換えず残し、一覧の操作に GET・HEAD の検証を足す形にする。置き換えると、一覧に載せ漏れた状態変更アクションへの POST が検証から外れ、CSRF の守りが後退する。保険として従来の POST 検証を残すことで、一覧が不完全でも POST は守られる。
- 2026-10-11 / yamamoto・Claude: 上の 2026-10-10 の決定（#505 で `where()` の中でエスケープする）を改める。`where()` だけが値をエスケープすると、DBAPI の取り決め（呼び出し側で安全化してから渡す）と食い違い、先にエスケープしている外部プラグインでは二重エスケープになる。1.2.2J と同じく `where()` は元の仕様に戻し、安全化していなかった呼び出し側を `db()->escape()` / `(int)` で直した（main は `fix/where-callsite` の PR）。取り決めそのものを変える（値のバインドへ移る）のは、PDO 移行（#453）のフェーズ 2 で扱う。
- 2026-10-12 / yamamoto・Claude: id を読む関数は、受け取り元ごとに `get_intvar()`（GET）・`post_intvar()`（POST）・`request_intvar()`（GET と POST の両方）の 3 つにし、その処理が実際に呼ばれる方法に合わせて選ぶ。`request_intvar()` をどこでも使うと「GET でも POST でもよい」という曖昧さを広げ、GET だけで呼ばれていた処理が POST でも動くようになるため。置き換えでは、元の `getv()` / `postv()` / `anyv()` に対応する関数を使い、受け付けるメソッドを変えない。状態を変える処理を POST に限るかどうかは、M2（CSRF）の範囲で扱う。
- 2026-10-12 / Claude: 再調査の結果を受けても、計画の方針（M1〜M4）は変えない。M1 の範囲に「権限の確認の有無をそろえる」ことと、下書き（リビジョン）の API へ渡す値も含める。
- 2026-10-13 / yamamoto・Claude（レビュー反映 #566）: M2 は、リソース系だけを先に出す案をやめ、一つの PR で一覧全体を入れる。一覧の置き場所とヘルパー名を後から揃え直す二度手間を避けるため。Artifacts の「受け付ける・付ける・必須にする」の 3 コミットには分けず、一括で入れた（受け付ける側と付ける側を同じ PR で揃えたため、途中の状態を残す必要がなかった）。
- 2026-10-13 / yamamoto・Claude: 2026-10-10 の「すべてを POST に変える案は採らない」を改め、POST への切り替えを M5 として行う。GET は状態を変えないという HTTP の取り決めに沿うためと、URL に載ったトークンがアクセスログ・履歴・Referer に残り、リンクの先読みや開き直しで操作が走る余地をなくすため。M2 で呼び出し元を `EvoCsrf.url()` / `csrfUrl()` に揃えたので、置き換えは機械的にできる。M2（PR #566）は GET＋トークンのまま先に入れる。CSRF の穴は M2 で塞がっており、POST への切り替えは processor の入力の読み方（M1 の「受け付けるメソッドを変えない」）も変えるため、別に検証する。
- 2026-10-13 / Claude: 2026-10-10 の決定（シェルの fetch はヘッダー、フルページの遷移は URL）を改め、GET で状態を変える呼び出しは、シェル経由でも URL にトークンを付ける。シェルが同じ URL をヘッダーなしで開き直すことがあるため（Surprises & Discoveries の 2026-10-13 を参照）。ヘッダーはこれまでどおりメソッドによらず付ける。
- 2026-10-13 / Claude: 一覧には、更新系のアクションに加えて保存系の processor（POST で呼ぶもの）も入れる。POST はもともと検証しているので正規の操作には影響せず、GET で到達したときに実行させないため。モジュールの実行（`a=112`）は、更新するかどうかがモジュールの実装次第で、モジュール内のリンクがすべて影響を受けるため入れない。ツリーの開閉状態の保存やメッセージの既読化など、表示のための軽微なセッション・状態の書き換えも入れない。
- 2026-10-13 / Claude: 表側の QuickManager のログアウトリンクは、表側に `csrfUrl()` が無いため、管理画面と共有のセッションから最新のトークンを読んで付ける。ログ画面の「ログを空にする」リンクは言語文字列の中にあるため、表示時に URL を置き換える。
- 2026-10-13 / Claude（M3）: lint は字句（`token_get_all()`）だけで判定し、同じファイルの中でリクエスト値を代入した変数・配列を上から順に追う（関数の本体は別のスコープ）。代入し直しで汚染を外すのは、汚染したときと同じブロックか外側で代入したときだけにする（条件・ループの中だけの代入では、通らない経路に元の値が残るため。PR #592 の Codex レビューで指摘）。比較・判定・整数化・エスケープ・ハッシュを通った値と、DB の呼び出しの戻り値は追わない。許可リストでの検査や、別の関数での検証までは追えないため、誤検出は書き方を直すか、行末の `// security-lint: ignore 理由` で抑止する（理由は必須）。初回の実行では、誤検出は lint 側を直し、残ったものはすべて実際に直した（抑止は 0 件）。
- 2026-10-13 / Claude（M3）: `sql-embed` の対象は計画どおり `manager/processors/` に限る。`js-escape` は、外部のライブラリ（`manager/includes/controls/`・`manager/media/`）を除いた `manager/` 全体を見る。`csrf-action` は、`manager/index.php` で `$prc_path` の processor を読み込むアクションを対象にし、一覧に入れないものは lint の除外リストに理由付きで書く（今はモジュールの実行 `a=112` だけ）。表示用の画面（`$action_path`）でサブ操作によって状態を変えるもの（`a=31` など）は、字句からは判定できないため対象にしない。
- 2026-10-11 / Claude: その PR では、id を `(int)` で整数にしている。M1 で `request_intvar()` / `post_intvar()` に揃えるときに、これらも置き換え対象に含める（`(int)` は SQL としては安全だが、`"5abc"` を `5` として扱う）。

## Context and Orientation

用語:
- **processor**: 管理画面で保存・削除・公開などの処理を行う PHP ファイル。`manager/processors/` 以下にあり、`manager/index.php` の `switch (manager()->action)` から、URL の `a`（アクション番号）に応じて読み込まれる。
- **アクション番号（`a`）**: 管理画面の URL の `index.php?a=61&id=5` の `61` のように、どの画面・処理を動かすかを示す番号。
- **CSRF**: ログイン中の利用者を、本人の意図しないリクエストへ誘導して操作させる攻撃。対策として、正規の画面だけが知っている値（CSRF トークン）をリクエストに付けさせ、サーバーで照合する。
- **シェル（EvoShell）**: 管理画面のメイン領域だけを fetch で差し替える仕組み（`manager/media/script/shell.js`）。

現状:
- リクエストの値は `getv()` / `postv()` / `anyv()`（`manager/includes/helpers.php`）で読む。id を数値として読むヘルパー `request_intvar($key)`（`helpers.php`）はあるが、正規表現で確かめた**文字列**を返し、使っている箇所と使っていない箇所が混在している。整数への変換の有無も、processor ごとにばらばら。
- `where()`（`manager/includes/extenders/ex_dbapi.php`）は値をエスケープしない。DBAPI 共通の取り決めとして、呼び出し側で `db()->escape()` または `(int)` してから渡す。`$field` と `$op` もそのまま埋め込まれる。`db()->update()` / `insert()` の配列の値も同じ（エスケープされない）。
- CSRF トークンの実装は `manager/includes/csrf_token.php`。トークンはセッション単位で、検証しても消えない（複数タブのため）。受け付ける場所は POST の `csrf_token`、`X-CSRF-Token` ヘッダー、URL の `csrf_token`（`getRequestCsrfToken()`。URL は M2 で追加）。
- 検証は `manager/includes/accesscontrol.inc.php` で行う。M2 より前は `is_post()` のときだけで、GET は検証していなかった。M2 で、POST はすべて、GET・HEAD などは `csrfProtectedActions()` の一覧に該当する操作だけ検証するようにした。
- クライアント側は `manager/media/script/csrf.js` が、POST のフォームに hidden の `csrf_token` を補い、同一オリジンへの fetch / XHR に `X-CSRF-Token` ヘッダーを付ける（M2 より前は GET 以外のときだけ。M2 でメソッドによらず付けるようにした）。URL へトークンを付けるときは、PHP の `csrfUrl()`・JS の `EvoCsrf.url()` を使う。トークンは `header.inc.php` が出す `<meta name="csrf-token">` から読む。
- 値を JS へ埋め込むときは `js_literal()`（`helpers.php`）、HTML は `hsc()` を使う（AGENTS.md の「出力のエスケープ」）。

## Plan of Work

M1（入力の受け取り）では、`request_intvar($key)` を「正の整数なら int、それ以外は 0」を返すように改め、**受け取り元（GET / POST / 両方）に関わらず、整数の検証はこの関数に通す**。POST だけで受け取りたい処理のために、同じ検証を POST 限定で行う `post_intvar($key)` も用意する（`(int) postv()` は使わない。PHP の `(int)` は `"5abc"` を `5` にしてしまい、「数字以外を含む id は 0」を満たせないため）。既存の 47 か所の呼び出しで、戻り値を文字列として比べている箇所がないか確かめてから変える。そのうえで、processor が id を `getv()` / `anyv()` / `postv()` で直接読み、整数に変換せずに使っている箇所を棚卸しし、この 2 つのヘルパーへ置き換える。カンマ区切りの複数 id を受け取る処理は、各要素を整数にしてから使う。権限の判定（`checkPermissions()`）と、その後の更新で、必ず同じ整数の値を使う。複数 id を受け取る処理では、すべての id について権限を確かめる。下書き（リビジョン）の処理では、`manager/includes/extenders/ex_revision.php` の関数へ渡す前に整数にする。棚卸しの一覧には、各 processor の権限の確認のしかた（リソースごとの `checkPermissions()`／`hasPermission()` だけ／ログインの確認だけ）も書き、更新する処理なのに確認が足りないものは、同じ PR で確認を足す。

M2（CSRF）では、`manager/includes/csrf_token.php` に「状態を変える操作の一覧」と、それを判定する関数を置く。一覧に含めるかどうかは「DB・ファイル・**セッション**を書き換えるか」で判断し、表示だけの画面は含めない。**同じアクション番号で表示と更新を兼ねる処理がある**ため、判定はアクション番号だけでなく、必要に応じてサブ操作（`a=31` の `mode=delete` など）も見る。将来的には更新処理を別アクションに分けるのが望ましいが、この計画の範囲では、番号＋サブ操作の組で一覧を定義する。`accesscontrol.inc.php` の検証は、**既存の「ログイン以外の POST は検証する」を残したうえで**、一覧に該当する操作には GET・HEAD などの検証を**足す**（置き換えではない。置き換えると、一覧に載せ漏れた状態変更アクションへの POST が、今まで効いていた検証からも外れてしまう。保険として従来の POST 検証を残す）。これで、一覧が万一不完全でも、POST の守りは後退しない。あわせて、現在の POST 検証が `a=8`（ログアウト。セッションを破棄する更新操作）を「ログイン処理」として検証から外しているのは誤りなので、除外するのはログイン（認証前でトークンを持てない）だけにし、ログアウトは検証対象に戻す（一覧にも含める）。`getRequestCsrfToken()` は、POST の値・ヘッダーに加えて GET の `csrf_token` を受け付ける。クライアントでは、`csrf.js` が同一オリジンへの fetch / XHR に、メソッドによらずヘッダーを付ける（`shell.js` の GET もこれで付く）。フルページの遷移のために、URL へトークンを付ける共通の関数を、PHP（例: `csrfUrl($url)`）と JS（例: `EvoCsrf.url(url)`）の両方に用意し、状態を変える操作へのリンク・`location.href` の組み立てをこれに置き換える。

M3（CI での検出）では、`.github/scripts/security-lint.php` を作り、次を検出したら終了コード 1 で終わるようにする。processor の中で、`getv()` / `anyv()` / `postv()` の戻り値を SQL の文字列へ直接埋め込んでいる書き方。リクエストの値を、`db()->escape()` / `(int)` / `request_intvar()` を通さずに `where()` / `and_where()` の値や、`db()->update()` / `insert()` の配列の値へ渡している書き方。`<script>` の文脈で `addslashes()` や `db()->escape()` を使っている書き方。`manager/index.php` で processor を読み込むアクションのうち、状態を変えるのに一覧へ登録されていないもの（判定できないものは、一覧か除外リストのどちらかへの明示を求める）。既存の違反は、M1・M2 の完了時点で 0 件にする。GitHub Actions のワークフロー（`.github/workflows/security-lint.yml`）から PR ごとに実行する。

M4（検証）では、`.claude/skills/adaptive-validation-runner` の検証環境で、M1〜M3 の確認スクリプトを main と比べて流す。

M5（POST への切り替え）では、`csrfProtectedActions()` の一覧にある操作を、GET＋URL のトークンから POST へ移す。クライアントには、URL とパラメータから POST を送る共通の関数（例: `EvoCsrf.post(url, params)`。シェル内では `EvoShell.submit()` を通し、シェル外ではフォームを作って送る）を用意し、M2 で `EvoCsrf.url()` / `csrfUrl()` に揃えた呼び出し元をこれに置き換える。PHP が出力するリンク（`<a href>`）は、ボタンとフォーム、またはこの関数を呼ぶ形に変える。processor は、id などを POST から読むように改める（`get_intvar()` → `post_intvar()`）。最後に `accesscontrol.inc.php` で、一覧の操作は POST 以外を 405 で拒否する。URL へトークンを付ける `csrfUrl()` / `EvoCsrf.url()` と、GET の `csrf_token` の受け付けは、外部のプラグインのため 1 リリースは残し、そのあと外す。

## Validation and Acceptance

- ログイン中の管理者が、管理画面のリンク・ツリーのメニュー・ボタンから、公開・非公開・削除・複製などの操作をすると、これまでどおり成功する（シェル経由と、フルページの遷移の両方）。

- id に数字以外を含めて送ると（`5abc` など）、処理は id=0 として扱われ、別の既存レコードが更新されない。SQL のエラーもログに出ない。

## Idempotence and Recovery

各マイルストーンは独立した PR にでき、途中で止めても既存の動作は壊れない順に進める。M2 は、まずトークンを「受け付ける」変更（ヘッダーと URL のトークンを読む・クライアントが付ける）を入れてから、最後に「必須にする」変更を入れる。必須化で問題が出た場合は、アクション一覧から外すことで、そのアクションの **GET・HEAD の検証だけ**を止められる（既存の POST 検証は残っているので、POST の守りは変わらない）。棚卸しのコマンドは何度実行しても結果は変わらず、置き換えの進み具合の確認に使える。
